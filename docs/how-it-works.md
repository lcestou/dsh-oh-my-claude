# How it works

The engine under the plugin: which process runs, how a session is kept, what happens on a restart, and how the stream reaches dsh. The panel and its tabs are on [their own page](panel.md). Remote boxes and second accounts are on [Remote boxes and accounts](remote.md). Back to the [README](../README.md).

## Where things live

The plugin runs Claude Code as a child process of dsh, so everything is on the machine that runs `dsh web`:

- Binary: the `command` config key, `claude` by default. A bare name is looked up on that process's `PATH` and then in the usual install folders. An absolute path is used as it is.
- Config dir: the plugin's `configDir` if set, else `$CLAUDE_CONFIG_DIR` if set for the dsh process, otherwise `~/.claude` of that user. Transcripts (`projects/`), `settings.json` and the login token all live there, the same place a terminal `claude` on that machine uses.
- Login: done once, in a terminal on that machine, with `claude auth login`, or from the Log in button described next.

The panel's first line shows which binary, which config dir, which host and which account dsh sees. If it says not logged in, that is the fix. The model picker says so too. A mount whose claude has no login is listed as `<name> (not logged in)`, from one `claude auth status` at mount and from every probe the panel runs after that. The models stay listed, so a session already on that box can still show the error a turn produces.

### Log in and Log out

Every row in Settings → Oh My Claude → Boxes offers the same Log in and Log out: this box, an ssh box whichever way it is reached (ssh, Tailscale, WireGuard), and a linked dsh box, whose own copy of this plugin runs them on its box.

Log in runs `claude auth login` under a local PTY (`script`, or `ssh -tt` for a box), the CLI's own login, so the terminal on that box and every Claude the plugin starts there share it. On a box with a browser, the CLI opens the sign-in tab itself and the approval reaches it over loopback, no code. When the sign-in page shows a code instead, paste it in the row. Once the process exits, the plugin asks that box's `claude auth status` whether the login took, the row flips, and a session whose turn had failed for want of a login shows a Log in card above its composer with the same flow.

Log out runs `claude auth logout` on that box and kills its running Claude processes, so nothing keeps answering on a login that is gone. Each session resumes from its transcript on its next message. A token from the earlier `setup-token` flow, still under `ssh-tokens/`, keeps being injected as `CLAUDE_CODE_OAUTH_TOKEN`, and its pill says "panel token" until Log out forgets it.

A second instance keeps its own login. With no `claude` on PATH, the row says so instead, and the plugin does not install it.

An `ANTHROPIC_API_KEY` in dsh's environment wins over the login: in `-p` mode the CLI bills that key and says nothing. dsh reads the `.env` of the folder it starts from, and the plugin hands dsh's environment to `claude`, so a key kept there for another tool would move every session onto per-token billing unseen. The CLI's init frame names the source, and when it is the environment variable the session gets one reasoning line at its start saying so, once per process. A key configured through `apiKeyHelper` is a choice and gets no line.

## Models

The picker is filled from the Anthropic Models API, using `ANTHROPIC_API_KEY` if set, otherwise the access token Claude Code stores in `~/.claude/.credentials.json`. On macOS the CLI keeps that login in the Keychain instead, so when the file is missing or expired the token comes from the `Claude Code-credentials` entry, for the default `~/.claude` only. It is cached ten minutes, and the hardcoded list in `src/adapter/catalog.ts` is the fallback. To cover a box with no saved CLI lineup yet, the first listing of a boot starts one `claude -p` and asks it `list_models` with no prompt. It waits up to five seconds, and the answer goes to `cli-models.json` for later boots. An ssh box skips this and learns its lineup from its first session. Context window and effort levels come from the same response, and picking an effort in dsh maps to `--effort`.

`settings.json` then gets the same say the terminal gives it, read fresh on each listing. `modelPicker.options` adds its rows (dropping the built-in lineup when `replaceBuiltInOptions` is set), and `availableModels` allows only the families, versions or ids it names, with the Default row surviving either way. A row of the CLI's own lineup normally takes the catalog's name for its model, so `sonnet` reads "Claude Sonnet 5". The exception is an alias someone named on purpose: `ANTHROPIC_DEFAULT_SONNET_MODEL_NAME` and its siblings, in `settings.json`'s `env` or exported where dsh starts, are how a router such as CC Switch says which model an alias really reaches, and a row the CLI reports under that name keeps it. The plugin adds rows of its own the same way, for a model no lineup lists, such as a name a local router sends to another model. They come from `customModels` in the plugin config and from the Add a model form in the Settings card's Models block, which keeps one list per mount in `custom-models.json` under the plugin's state (`PUT /custom-models` replaces a mount's list and emits dsh's `llm/models-updated`). An entry can also give the model's context window and effort levels, which a `settings.json` row cannot, and the allowlist filters these rows like the rest. Only the listing is filtered, so a session already on a model the allowlist excludes keeps resolving it, as the terminal does. The plugin's own cut comes last: `hiddenModels` from the plugin config, then the Settings card's Models block, a switch per model and per box, stored as a `hideModel:<provider>:<id>` hint in the hints store (the provider being the mount's id), so each box keeps its own list and every browser sees the same ones; `GET /models?all=1` serves that block every mount's unfiltered rows with each one's hide state, a write to one of those keys emits dsh's `llm/models-updated` so the open picker reloads, and removing a box drops its keys. The same file's `maxEffortLevel`, and a per-model `modelSettings.<id>.maxEffortLevel` that overrides it, cap the effort levels a model offers, so the picker no longer shows a level the CLI would clamp. The value is read from that one file, not merged across settings scopes the way the CLI does.

The listing also follows where the mount's requests go, so the menu holds only models that can answer. That is read from what a router leaves in Claude Code's own config, not from any router's files: `ANTHROPIC_BASE_URL` and the `ANTHROPIC_DEFAULT_<ALIAS>_MODEL` and `..._MODEL_NAME` variables, taken from the environment dsh was started with, then `settings.json`'s `env`, then the managed settings file, each outranking the one before as it does for the CLI. A mount is in one of three states. It is direct when no base URL is set, when it is Anthropic's, or when the endpoint forwards to Anthropic (the same unauthenticated probe the "Proxy reaches Anthropic" switch uses, kept per URL for a minute and never waited on by a listing). It is routed when the endpoint answers and is not Anthropic. An ssh box answers for itself, since its files, its shell and its loopback are not this one's: the same variables are read there over ssh (the far shell's own, then that box's `settings.json`, then its managed file) and the probe is sent from the box with `curl`. Its answer is kept for a minute and asked again behind the next listing or turn, so a router switched on there shows up without a restart. Otherwise the state is unknown and every row is listed: a box that has not answered yet or has no `curl`, a Bedrock, Vertex or Foundry setup, where the CLI does not call the base URL, and an endpoint that does not answer. On a direct mount a row the plugin added for a model the catalog does not know is left out, because Anthropic would refuse the id. On a routed mount whose router took over aliases, Claude's own rows are left out instead and the menu is Default, the aliases the router named or pointed at a model of its own, and every row someone added or wrote into `modelPicker.options`. An alias counts as the router's only once the CLI's lineup reports it that way, so a lineup from before the switch never empties the menu, and a gateway that renames nothing keeps all of Claude's rows. "Also list Claude's own models" in the Settings block (`routedClaude:<provider>` in the hints store) keeps them on a routed mount.

A router's row has no window anyone can look up: the alias still resolves to a Claude id, and Claude Code manages the session against that model's figure (measured on 2.1.322 with `get_context_usage`: 1,000,000 for `sonnet` behind a router, whatever the model behind it holds). So a row the router took over reports 200,000 until its real size is set on the row in Settings, where it is kept by alias as `routerWindow:<provider>:<alias>` in the hints store. An added model's size is part of its entry and is set the same way, on its row, next to its Remove. A session on either kind of row is started with that window in `CLAUDE_CODE_MAX_CONTEXT_TOKENS` and `CLAUDE_CODE_AUTO_COMPACT_WINDOW`: the first sizes a model the CLI has never heard of, the second caps one it knows, and with both the CLI reports the number given. The window joins the spec that keys the process, so a size changed in Settings reaches a running session on its next turn. A window you chose yourself stands: with `autoCompactWindow` in a settings file, or either variable already set, the plugin sets neither.

A turn a router answers is kept apart in the session's accounting. The CLI prices every turn at Claude's API rates whatever answered it, so each such turn's record carries `via`, the host it went to, set when the endpoint in force for the turn answered as not Anthropic. The cost pill, its dialog and `GET /turns` add up money over the other turns only; time and tokens count for all of them, and the dialog says how many turns went through a router. The plan usage rows are a separate read of Anthropic's own usage endpoint and never see a routed turn. A workspace's own `.claude/settings.json` and `.claude/settings.local.json` are not read for the listing, which is per mount, not per workspace. A turn does read them: they outrank the user's file for the CLI, so a session can be pointed somewhere other than the box says, and the base URL that decides the session's process and the "Proxy reaches Anthropic" flag is the one in force in its workspace. The usual way to meet this is a `~/.claude/settings.local.json`, which is the local file of every session opened in the home folder.

A switch made while dsh runs is followed without a reload. The plugin watches the directory that holds each settings file, acts only on those two file names, and compares the routing variables with the last ones it saw, so the CLI's own writes there cost nothing. On a real change it asks the CLI for its lineup again (`list_models` with no prompt, as at boot), emits `llm/models-updated` so open pickers reload, and publishes a hints event so the Settings rows re-read. The variables it last saw are kept beside `cli-models.json`, so a router switched while dsh was down is noticed at the next boot. The base URL a settings file sets joins the spec that keys a session's process: a session started before the switch is replaced on its next turn and resumes, because a process reads its environment once. Nothing treats a row that is only out of the menu as a retired model. A remembered model (a workspace's last one, the new-session default) is judged against every row the mount can name, and the repair that moves a session off a renamed id runs only on a direct mount. A session left on a model that needs a router shows dsh's "Select model" in its seat, and a turn sent anyway fails with a sentence that says the model needs the router, in place of the API's "it may not exist or you may not have access to it". A 401 on a turn whose key was set in a settings file's `env` (`ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY`, which is what a router writes beside its address) is not treated as a lost login: the box is not marked logged out, and the failure names the endpoint that refused the key. When the address and the key were set by two different files, it says which, since that is how a router's key reaches an endpoint that was never the router's.

The API dates some ids (`claude-haiku-4-5-20251001`) and leaves others alone, while the fallback list and the CLI's picker use the undated form. Since dsh keys a model by its id, an API id whose undated form is one the fallback list names is advertised undated. Otherwise every switch between the API and the fallback retired the model you had enabled and offered an unselected copy of it. An id the fallback list does not name keeps whatever the API called it. The CLI's own picker is held to the same rule. Its rows lead the lineup with the CLI's windows and effort levels, but a row landing on a model the catalog already knows takes that model's id and name rather than the alias, so a model is spelled the same before and after the CLI answers `list_models`. A row nothing names is named from its id (`claude-opus-5-5` reads "Claude Opus 5.5"). Only `default` and the `[1m]` variants keep an alias, having no stable id to take.

Once the CLI has answered, its lineup decides what the picker shows. A model from the API or the fallback list that the CLI does not offer is left out, with two exceptions. The plain id behind a `default` or `[1m]` row stays, so a session bound to it finds its row. An API row released (by the API's `created_at`) after every model the CLI offers is one the installed CLI predates; it stays, and its description reads "Newer than the installed Claude Code; update the CLI to unlock it." A model Anthropic retires therefore leaves the picker when Claude Code drops it, with no list to edit. A session bound to a model that left still resolves its name, window and effort levels from the API cache or the fallback list, so its turns run. When it is opened while idle, the plugin moves it to the newest listed model of the same family (Opus 4.5 to Opus 5.5); a model with no listed family stays put and dsh's composer shows "Select model". To keep a model listed, add its full id (`claude-opus-4-5`) to `modelPicker.options` in settings.json.

## Sessions

Each dsh session gets a deterministic Claude Code session id. The first request starts it with `--session-id`. Later requests find the transcript under `~/.claude/projects/<cwd>/` and pass `--resume`, sending only what followed Claude's own last reply: the new turn, plus any turns another model made while the session ran on it. Another model's tool calls and results go over as text, each input or output capped at 2,000 characters, since Claude never saw them. Reopening an old dsh session resumes the same Claude Code session, with all its tool history. Forked sessions start fresh from the full dsh transcript. The child runs in the dsh session's working directory, so Claude Code sees the right CLAUDE.md and project files.

A terminal `claude` opened in that same directory lists them under `/resume` like its own. That takes one thing from the plugin. Every child runs with `CLAUDE_CODE_ENTRYPOINT=dsh-oh-my-claude`, because a print-mode CLI otherwise records `entrypoint: sdk-cli` and the picker hides every sdk-cli, sdk-ts and sdk-py session (Claude Code 2.1.268). Sessions recorded before this setting stay hidden in the picker. `claude --resume <session id>` still opens them, the id being the transcript's file name under `~/.claude/projects/<cwd>/`. Enter the directory by its real path, since a symlinked path maps to a different transcript folder.

## One session, two places

A dsh session and a terminal `claude /resume` share one transcript file. Carrying a session between the two needs nothing switched on. Claude Code writes that file itself, so a terminal `/resume` opens with dsh's turns in it, and a session that has only ever run in a terminal is seeded into dsh from the same transcript.

What is optional is the live copy in one direction: terminal exchanges appearing in an already-open dsh tab as they land. That is the Terminal mirror, marked experimental in the settings panel and off by default. It is off because it holds a dsh turn open while it fills, and a prompt typed meanwhile can queue behind it. Turning it off does not affect moving a session between dsh and a terminal.

With it on, the plugin watches the transcript of every session dsh has loaded (inotify on this box, a `stat` over the shared ssh connection every 30 seconds for a session that runs on an SSH box). The terminal's rows carry `entrypoint: cli`, and the plugin's own carry `dsh-oh-my-claude`. So when a terminal exchange lands and the file settles, the plugin opens a turn of its own in the dsh session: the prompt as a user message, the reply as the assistant's, tool calls drawn inline the way a live turn draws them. Nothing goes to Claude for it, since the transcript already holds both sides, and the live Claude process is marked stale so the next real message resumes from the transcript with the terminal turns in context. One exchange per turn, in order. An exchange that lands during a dsh turn follows it, and an archived session is left alone until it is opened again. Where each watch stands is kept in `watch.json` under the state directory, so a restart carries on where it left off, and `resume.log` records each `watch` and `mirror`. What that gives, side by side:

| Start here | Continue there | What happens |
| --- | --- | --- |
| dsh | terminal `claude /resume`, same directory | The picker lists the session; it opens with the whole history. |
| terminal | dsh, the session open in a tab | Each exchange shows in the tab within seconds; the next dsh message knows it. |
| terminal | dsh, the session not open | Shows the moment the session is opened; nothing opens by itself. |
| terminal only | dsh, never spoken there | The panel's session list offers the transcript; opening it seeds a dsh session that keeps the same Claude id. |
| dsh | terminal, while both are open | The terminal never re-reads the file: it sees dsh's turns only on its next `/resume`. |

The last row is the one limit of the design, and it comes from Claude Code, which follows the chain the transcript's last row belongs to when it resumes. A terminal that keeps typing after a dsh turn forks the file, and the next dsh turn takes that fork as the truth. One side live at a time is the rule.

## Temporary sessions

Type `/temporary` in a session to toggle it. From the next turn its Claude process runs with `--no-session-persistence`, so nothing lands under `projects/` for it, and the session is never resumed on the Claude side. A dsh restart continues it from dsh's own log instead. Type `/temporary` again to switch back. The mark lives in memory, so it survives a plugin reload but not a dsh restart.

## Ultracode

Type `/ultracode` to turn Claude Code's ultracode on or off for a session, or `/ultracode on`, `/ultracode off`. It is switched inside the running Claude process, with no relaunch, and remembered for the session's next process. dsh answers a command before Claude Code can, so the reply says the request went out; `/ultracode status` says what Claude Code read back: on, off, or that the session's model does not offer it.

## Process

One `claude` process stays alive per dsh session (`processIdleMs`, default 30 min; `maxProcesses`, default 4, evicts the longest idle). Turns after the first start in about a second because hooks, CLAUDE.md and MCP servers are already loaded. A change of model, effort or working directory replaces the process, and the Claude session is resumed, so nothing is lost. A permission mode is switched live, except Bypass (see [Permission mode per session](#permission-mode-per-session)).

### Idle watchdog

`idleTimeoutMs` stops a process that produces nothing for that long, but not silently. Half a timeout before the stop (60 s when the timeout is two minutes or more), a reasoning row announces the countdown, and the session header shows `stopping in Ns` with an Extend button that pushes the deadline out by a full timeout. A tool call in flight gets twice the timeout, because a test suite can be quiet for a long time and a call that never returns should still end. An approval, a question or a plan review waiting for your answer holds the watchdog off altogether: the countdown does not start, and nothing is stopped, until the dialog is answered. `GET /dsh-oh-my-claude/idle?session=` and `POST /idle/extend` are the routes behind the chip.

## Approvals and questions

With `approvals: true` (default) the child runs with `--permission-prompt-tool stdio`. When Claude Code would ask permission, dsh's own approval dialog appears. Approve runs the tool, and Deny tells Claude the user refused. Claude's `AskUserQuestion` becomes a dsh question form, and the answer goes back to Claude.

Under Full Access nothing asks, except plan review. When Claude leaves plan mode (`ExitPlanMode` arrives as a permission request carrying the plan), dsh's own Plan review panel shows it with Approve and Keep planning. Approval lets the tool run, and anything else goes back to Claude as "the user chose to keep planning" with the typed feedback. Each ask also shows as a `⚑ approval: Tool …` or `❓ question …` row.

## Permission mode per session

dsh's access shield by the composer is the control, in a Claude session with Claude's rows: Plan (read-only), Ask and Accept edits (workspace write), Auto, Don't ask and Bypass (full access). A pick first switches dsh's preset through its own `/permission` command when the mode needs another one. It then stores the Claude override per session under the instance state dir (`permission-modes.json`), used for `--permission-mode` at the next spawn or resume and pushed to a live process with the CLI's `set_permission_mode` control request. Bypass is the one mode the CLI takes live only from a process launched in it, so picking Bypass on a session running in another mode is stored and applied when the next turn respawns the process, and the menu says so. The capsule shows the mode the running process is in (`liveMode` in the route's reply), not the stored pick, so a refused or deferred switch never reads as done. A transcript opened from the terminal keeps the mode its last prompt ran under (the CLI stamps every prompt row with `permissionMode`), clamped to dsh's preset. The override can only be as loose as dsh's preset maps to (`plan`, `acceptEdits`, `bypassPermissions`), and the server refuses a looser one. dsh's trigger and menu are kept and relabelled, so other providers see dsh's shield unchanged. Routes: `GET`/`PUT /dsh-oh-my-claude/permission-mode`.

## Secrets

Values of environment variables whose name looks like a secret are masked in Claude's tool results before they reach the session log (`redactSecrets`), since the CLI inherits dsh's environment and a `cat .env` would otherwise persist verbatim. Only the values this process can see are known, and secrets read from files are not.

## Restarts

With the Settings switch "Keep Claude running across dsh restarts" on, the default, a dsh restart does not touch Claude. Each `claude` process is owned by a keeper (`lib/server/keeper.js`, one per session under `~/.local/state/dsh-oh-my-claude/keepers/<id>/`, launched in its own systemd user scope so the service's cgroup kill misses it). The keeper owns Claude's pipes, buffers its output while no dsh is attached (bounded, oldest lines dropped with a notice), and dsh talks to it over a unix socket. It numbers each line and keeps it until the plugin confirms a turn used it, so a reply Claude finishes while the old dsh is still shutting down is replayed to the new one rather than lost with the process that read it. On boot the plugin reattaches to every keeper whose Claude is still alive, and if Claude replied or finished a background task while dsh was away it opens a turn that shows it, with a "reattached" notice as the next prompt. The CLI's own notices, such as the background-task snapshot it sends back when the plugin reattaches, wake nothing. The MCP bridge key lives in `mcp.key` in the state dir so a surviving Claude still reaches the new dsh's tools, though Claude's MCP client may still need to reconnect once after the restart. Kill semantics are unchanged: Stop, eviction and the idle timers end the keeper's Claude. A keeper nobody attaches to for `processIdleMs` (never under five minutes), while Claude writes nothing, closes Claude's stdin and exits, so a dsh that is gone for good leaves nothing running. Each keeper is tagged with the dsh profile that started it, and a dsh reattaches only to its own and leaves the other's restart nudge alone, so DSH Web and DSH Desktop, which run separate profiles, keep their sessions apart on one `~/.local/state/dsh-oh-my-claude`. Two dsh on the same profile directory still share. Frames the CLI sends between turns (a late answer to a control request, `keep_alive`, `rate_limit_event`) wake nothing; a reattach opens a turn for Claude's own output, a running tool's progress or a finished background task. With the switch off, Claude runs as dsh's child through its subprocess seam and a restart ends it; keepers still running from before the flip are reattached, drain what they hold, and are replaced on each session's next turn.

With the switch off, or `spawn: node` or `dsh` in the config, a dsh restart kills every Claude Code child. Sessions that had a turn running are written to `~/.local/state/dsh-oh-my-claude/busy.json` as the turn starts and removed as it ends. About ten seconds after dsh comes back, each one still listed gets a plugin notice as a real prompt ("dsh restarted while this turn was in progress…"), the Claude session resumes with `--resume`, and the work continues without anyone typing. Sessions that were idle are left alone.

A hot reload of the plugin is not a restart: a profile edit to its row, a toggle off and on, or a code update disposes the plugin's scope and mounts a fresh instance in the same dsh process. The Claude processes live on `globalThis` and stay, and so do their keepers: the new instance's adoption skips a keeper whose session already has a registered process, rather than killing it as an older duplicate. dsh does not abort a model call already streaming, so the step in flight keeps running on the old instance. Its scope's services are gone, so the old instance reaches dsh through the new instance's context from the moment that one is mounted. A step that still dies after a reload (no result, no Stop, no shutdown) keeps its `busy.json` mark, and the new instance resumes the session: a Claude that is still running has what it wrote drained into a new turn, the way an adopted keeper's is, and a dead one gets a reload notice as a prompt so its next turn resumes the Claude session. If no instance is mounted again within three minutes, the mark waits for the next boot's nudge. A failure to build a coalesced event for the open tabs is dropped instead of thrown, since that throw, from a timer, ended dsh on 2026-11-12.

Two guards keep this path from doing harm. A boot within a minute of the previous one is treated as a crash loop and nudges nothing, and the busy list is left for a later healthy boot. A session whose durable inbox already holds an unconsumed restart notice is not nudged again. The trace of every boot is `resume.log` next to `busy.json`. The nudge starts one turn. For work that should keep going across restarts with nobody at the keyboard, put it under a dsh goal (`/goal` or `create_goal`). dsh's goal round driver starts the next round whenever the agent is idle with an armed goal, and since dsh disarms goals on session resume, the restart notice tells the model to rearm it with `update_goal` (action `resume`).

## Streaming

Text and thinking arrive as live deltas. Claude Code's own tool calls show as dsh's own tool cards by default, once the plugin's startup probe finds the running dsh loads them back (see [Native tool rows](panel.md#native-tool-rows)). Until then, or with the Settings switch "Native tool rows" off, they render inline in the stream. With rows on, the adapter appends `tool/call` and `tool/result` session events inside the open step, the same shape dsh's loop writes for its own tools. So `Bash`, `Read`, `Edit`, `Write`, `Grep`, `Glob`, `WebFetch` and `WebSearch` each get dsh's presenter for that tool, `MultiEdit` shares Edit's, and every other Claude tool keeps its own name on the generic row. Bash shows its description, and an edit shows the +/- badge from `meta.diffs`. Inline headers take dsh's own row typography too: the tool name, a 2 px dot and the summary in the tertiary colour, split out of the translator's `name · summary` line by the same client pass that lifts the glyph. dsh never runs those tools. Claude Code does, under the configured permission mode. Fable-class models return thinking blocks with an empty body, so no reasoning text appears for them, while local and Sonnet-class models stream theirs.

### Session statistics

dsh's Session statistics dialog reads a Claude session the way it reads any other, from the session log, so the figures mean this here. Time to first token runs from a step's start to the first byte of Claude's response: the plugin writes one whitespace token at that moment, which dsh times and does not draw, so a silent think and a message that goes straight to a tool call count from where they began. Tokens per second is the step's output tokens, thinking included, over the time from that first token to the step's end, and a step in which Claude ran its own tools keeps those waits inside that window, so a tool-heavy step reads low. LLM time is the wall time of Claude's steps, which include Claude's own tools, because dsh cannot see inside a step; Tool time is dsh's tools only, the relayed jobs, subagents and waits. With tool rows on, dsh closes its count of a step at the first tool announcement, so LLM time and the token rate cover only the lead-in to the first tool.

## Turn status

While a turn runs on a session this plugin drives, the status row under the last message takes Claude Code's look instead of dsh's blue `Deep diving...`: a spinner glyph played through Claude's own frames, a verb picked per turn from the CLI's list (`settings.json` `spinnerVerbs` is honoured, `append` or `replace`), Claude orange, the elapsed clock kept. After the verb sits a bracket the way the CLI's own line writes it, and on the CLI's terms: nothing for the first 16 seconds of a turn that has no tokens and no thinking word, then the clock (hours written as `1h 40m 42s`), the turn's running token count (summed across every message of the turn plus the estimate for a thinking block in progress, eased toward its target the way the CLI eases its own), and `thinking` while a thinking block is open. The word climbs the CLI's ladder (`still thinking` at 10s, `thinking more` at 20s, `thinking some more` at 30s, `deep in thought` at 45s), names the effort when dsh asked for one, and gives way to `thought for Ns` for two seconds once the block closes. On dsh 0.2 that row sits under the turn's content, where dsh draws its whale icon and `Deep diving...`, and scrolling up through a long turn takes it out of view. While it is off screen the same line (spinner, verb, bracket) repeats above the composer, in dsh's `conversation.input.dock` slot, wired by the same code as the row's so the verb and figures match. It is on by default; a switch in Settings > Oh My Claude ("Working line above the composer", hint `dockStatusOff`) turns it off for someone who wants only the line under the turn.

While dsh runs one of its own tools for Claude (a subagent, a background job, `job_output`), the step is closed and nothing streams, so the bracket names the wait instead: `running job_output for 151s`, the shape of the CLI's own `running tool for Ns`, with the clock and the count kept beside it.

Colours follow the CLI's spinner: a thinking burst past ten seconds warms the glyph, verb and word toward the theme's warning shade over the next ten, a response that goes quiet for ten seconds tints them toward the CLI's stall red, and the shimmer sweeps only while neither is up. The sweep follows the CLI's modes, which the `live-turn` body carries as `mode`: left to right and fast while the request is out, right to left and slow while a block streams, and while a tool runs the whole verb breathes between the accent and the shimmer instead of sweeping. The spinner glyph plays the CLI's eased two-second cosine, lingering on the end frames. The figures arrive over the plugin's event stream (below), at most once a second per session; a tab whose stream is down reads the `live-turn` route once a second instead, and a hidden tab reads nothing. Everything else is read from the CLI bundle. The row has no slot, so the client restyles it through a DOM watcher (`watchTurnStatus`), only when the session's provider is `claude-code`.

The word `ultrathink`, typed in the composer, waiting in the queue or sent in a message, takes the CLI's rainbow (one colour per letter, red through violet, wrapping), with the CLI's shimmer sweeping over it in the composer. `ultracode` takes the CLI's purple in the composer only, under the CLI's own matcher (a quoted or slash-command occurrence is left plain). Both go through the CSS Highlight API, so neither the composer nor the chat sees a DOM change. The same Claude orange tints the running dot beside each session in the sidebar under Workspaces, but only for Claude sessions. A second watcher (`watchSessionSpinners`) colours the matrix dot for sessions whose provider is `claude-code`, matched by their title in the row, and leaves any other provider's dot dsh's default. A session that changes to another provider mid-flight loses the tint.

When the turn ends, its header keeps a line the way the CLI closes a turn in the terminal: `✻ Crunched for 27s · done 3:21 AM`, in grey. The verb is one of the CLI's eight closing verbs (Baked, Brewed, Churned, Cogitated, Cooked, Crunched, Sautéed, Worked), picked per turn and stable across reloads, though not the same pick the terminal makes for that turn: the CLI hashes a message id the page never sees. The duration is dsh's own "Completed in 27s" ("Took 27s" before dsh 0.2.0-rc.2) and the time is the clock dsh prints under the reply, so a reloaded page draws the same line. Chinese reads `烘焙了 27s · 03:21 完成` on dsh's 24-hour clock. A turn you stopped reads the CLI's `Interrupted · What should Claude do instead?` in place of dsh's `Stopped`, and a failed one keeps dsh's `Failed`.

All of this colour is the Claude look switch in Settings. Off, or off per group, and the status row, links, send button, panel and rainbow fall back to dsh's own. The accent picker there recolours the lot. [The panel](panel.md#claude-look) has the switch.

## Event stream

Everything a tab used to ask the server for on a timer arrives on one stream instead: `GET /dsh-oh-my-claude/events?session=<open session>`, server-sent events, one connection per tab. It carries eight kinds, each body the same as the matching GET route's (`awaiting` without the route's `sessions` wrapper, `asides` without `claudeUpdate`): `live-turn` (at most once a second per session, `{}` when the turn ends), `awaiting` (every mount's open prompts, to every tab), `asides` (the `/btw` ring, the login card, the fallback note and the steer card), `idle`, `turns`, `hints`, `new-session-default` (the default for new Claude sessions after a write from any tab) and `permission-mode`. On connect the server sends the current value of every kind but `hints` and `new-session-default` for the session, so a reconnect needs no replay. A `ping` event every 25 s keeps a proxy's read timeout from closing an idle stream, and the response carries `X-Accel-Buffering: no` so nginx passes each event at once. The old timers stay as a fallback: while the stream has been heard from in the last 60 s they run every 30 s, otherwise at their old rates. A hot reload or a dsh restart closes every stream and each tab reopens one within a few seconds; a reopen that lands in the gap before the new bundle registers its route is answered 404, which closes an `EventSource` for good, so the tab checks once a second and opens a fresh one. Measured on this box on 2026-09-23 with `tools/playwright/poll-count.ts`: a running session's page went from 206 requests a minute to 18 (six of those are the context cache and two the usage ring, which the stream does not carry), a blank session from 80 to 4.

## Compaction

The CLI announces compaction with a `compacting` frame, goes silent while it summarises, then emits the boundary. Both ends show in the reasoning lane, and a failed compaction is reported. The `compacting` frame repeats every 30 seconds until the boundary arrives, so the announcement is written once and the repeats only keep the status row's clock moving. A 141-second compaction was measured on 2026-09-14.

dsh's own automatic compaction is left on for this plugin's routes, and from 1.1.x to 1.5.10 it was not. Claude Code compacts its own context and this plugin relays that, and dsh's pressure reading measures dsh's session surface, which keeps growing because `resume` sends the CLI only the tail, so in September dsh compacted on top of the CLI off a number that did not describe the CLI's context: 22 times in one day, about 100 seconds of Opus each, for summaries `selectTurns` sliced off anyway. The lever that turned it off was capacity: dsh asks an adapter for a model's context window through two methods, `prepareCall`, whose answer feeds the context ring and the readouts this plugin injects into it, and `resolveModel`, whose answer is what `compaction-basic` multiplies by its threshold ratio. The plugin answered the first and stayed quiet on the second, and dsh's between-step hook tolerated that with one warning.

dsh 0.2.2-alpha.2 added a second reader that does not tolerate it: its `agent/request` hook prices a model switch against the target's capacity and fails the whole request when there is none, so every switch between two Claude models answered "Cannot switch to claude-code/…: no context capacity" and dropped the typed message. Since 1.5.11 both methods report the same window, and dsh's compaction runs on Claude sessions again. Its measure is the prompt the CLI last reported (dsh's token meter reuses the provider's usage while the request envelope is unchanged), and compacting dsh's own copy never lowers that. So once a session passed the threshold, 80% of the window capped by the window less a 65,536-token headroom (800,000 tokens on a 1M model, 134,464 on a 200k one), dsh compacted before every step: 33 one-shot summaries of about 30 seconds each in one team member's turns on 2026-11-01, while the CLI's context kept growing past them. `compaction-basic`'s `modelPolicies` sets that threshold per route. `/compact` on demand is a separate path and never read capacity; `dsh-session-reference`'s capacity-scaled budget applies again.

`cliCompaction` (on by default) answers dsh's compaction of a Claude session with Claude Code's own. When the CLI is idle, at the start of a turn or under dsh's `/compact`, the plugin runs `/compact` on it and hands dsh the summary the CLI wrote to its transcript, so both sides compact once, with one summary, at dsh's threshold, which on default settings comes before the CLI's own. While the CLI is mid-turn (running, or waiting on a relayed tool call or a steer) it cannot take `/compact`, so the request is refused: dsh logs `step compaction failed: Claude Code is mid-turn; …`, records a failed compaction in the session log, which the chat does not show, and runs the step. The session compacts once its turn ends and it is idle. A subagent or team member does not, because dsh settles and disposes it the moment it is idle and its parent waits on that; it compacts at the start of its next turn instead. A forked one that inherits a history already past the threshold has it compacted before its first request, when it has no CLI yet, so dsh's one-shot summarizer answers that one and the child's CLI starts from the summary. A compaction the CLI makes on its own during a turn reaches dsh's copy the same way once the session is idle, without another model call. dsh keeps pricing the prompt the last request reported until the next one reports, so right after a `/compact` it can ask again; that is refused too ("Claude Code compacted this session already"), and the next request settles it. A session moving to another provider, a model picked mid-turn (dsh fails a model switch whose compaction fails), the terminal mirror and `cliCompaction: false` keep the one-shot summarizer. A pick is read from the `model/selection` dsh writes for it, which DSH Desktop's model picker does; an ACP client's pick stays in dsh's ACP bridge until its request runs, so a compaction just before that request runs `/compact` on the CLI instead, which costs one CLI compaction and still leaves dsh's copy summarized. Two leftovers are accepted, and only a model reading dsh's copy after a switch away from Claude sees them: a compaction at a turn's start keeps dsh's verbatim tail, 16% of the window, beside a summary that covers it too; and a compaction the CLI made mid-turn leaves the steps after its boundary in dsh's copy as the turn's last message only. dsh also runs its tool-result pruner, which needs no model, before it asks for a summary. Its figure is the CLI's last report less what the pruner took from dsh's copy, so the pruner can meet the threshold for a turn while the CLI's context stays as it was, and the CLI compacts a turn later. When it does ask, the span left to replace can be smaller than a summary of the whole conversation; dsh then turns the summary down (`summary is not smaller than the shadowed content`) and keeps its copy as it is, while the CLI is compacted all the same. Each decision is logged to `resume.log` as `compaction <session>: …`.

## Task progress

The CLI's subagent runner emits `task_started` when a task begins, `task_progress` frames as the task runs (carrying `last_tool_name`, `usage` token counts, a `description` the CLI rewrites per step, and a `summary` the model writes now and then once the plugin's `initialize` request asks for it), and `task_notification` when the task finishes or fails. The plugin keeps one reasoning block open per running task, so dsh renders each as a single collapsible row with the start line, progress updates as they arrive (tool name and token counts, the step's description, the summary), and the final status. Identical progress frames append nothing, so a chatty task does not fill its row with repeats. A task without a `task_id` renders as a single closed line. `background_tasks_changed` is silent, since it is list churn. Source: `src/translator.ts` and tested in `src/adapter.test.ts`.

Four `system` frames report a model switch, and the plugin reads each. `model_fallback` fires when the primary model is unavailable and the CLI drops to a `--fallback-model`. It draws one reasoning line and is turn-scoped, so the next turn tries the primary again. `model_refusal_fallback` is the safety-classifier switch, a flagged Fable request re-run on Opus. It draws a reasoning line naming the refusal category, and on the turn's stop it fires a desktop notice. The model picker follows only when that switch is `sticky` and session-scoped, since `retry`, `revert` and a `local` scope (a subagent or a `/btw` side-question) leave the session model alone. `model_refusal_no_fallback` is the paused case, a refusal with no retry, drawn as a blocked line while the `result` frame ends the turn on its own. `model_consent_fallback` is the usage-credit gate and shows the CLI's own sentence. Each switch is banked in the adapter's `sessionFallbacks` map and read back over `/side-questions`. Source is `src/translator.ts`.

## Todo panel

dsh clears its todo projection at every turn start. The adapter re-appends the last `todo/write` inside the open turn (`persistTodos`), so the panel keeps the list across messages and restarts.

## Images and files

Image attachments in the user turn are read from dsh's attachment store and sent inline as base64. A copy is kept under `~/.local/state/dsh-oh-my-claude/attachments/<hash>.<ext>` with the extension its media type calls for, since dsh's own stored object is named by hash with none and Claude Code's Read decides image-or-text by the name. A note after the prompt names that path, the display name and the size, so Claude can Read the image again, edit a copy, or hand the path to a subagent instead of only seeing the pixels. A file attachment needs nothing from the plugin. dsh-llm replaces every file block with a line naming the file and the read-only path it is stored under before any provider sees the turn, and Claude reads that path with its own Read tool.

## dsh tools over MCP

Every dsh tool the session's agent can see, except the shell and file ones Claude Code has natively, is served to the Claude process as an MCP server named `dsh` (`--mcp-config`, Streamable HTTP on the dsh web port, path `/dsh-oh-my-claude/mcp/<session id>`, guarded by a key kept in the state dir). Under DSH Desktop, whose web server answers 403 to anything but its own window, the same path is served from a listener of the plugin's own on 127.0.0.1 instead, on a port remembered in `mcp-port` so it survives a restart. Claude Code sees them as `mcp__dsh__*`: `subagent_local`, `researcher_local`, `list_agents`, `send_message`, jobs, goals, skills, web search, and `bash` (for long-running commands that you would run with `run_in_background`: dsh registers the job, shows its card and panel entry, and delivers the finish notice next turn; short foreground commands stay on native `Bash`). A subagent started this way is a real child of the dsh session. It runs on whatever route the preset pins, shows in the session header's subagent dropdown, and its completion notice reaches the next Claude turn as context.

Calls to those tools are relayed, not executed in the bridge. The adapter ends the current step with a real dsh `tool-call`, dsh runs the tool in its own loop (so a subagent shows the native card, the header count, and its completion notice like any dsh-native session), and Claude's MCP request is answered with dsh's result when dsh sends it back. If no live turn can take a call (idle process, a relay already pending), the bridge executes it directly as before.

In plan mode the bridge refuses every dsh tool that is not on a short list of tools that only read (listing jobs and agents, reading a job's output or a session's replies, web fetch and search, skills, asking you a question). Claude Code's plan mode runs an MCP tool marked read-only without asking, and the dsh tools the bridge relays carry that mark so parallel calls run side by side, so without the refusal a planning session could run dsh's shell or start a subagent. The list is in `src/plan-gate.ts`; a tool dsh adds later is refused in plan mode until it is added there.

Under a code-mode agent preset (dsh's `ptc`), where dsh offers the model only `run_code`, the bridge offers Claude `mcp__dsh__run_code` as its only dsh tool, beside the plugin's own `open_session`, `prompt_session` and `wait_session`. Claude reaches the other dsh tools from inside a `run_code` program, a direct call to any of them is refused, and `run_code` needs a live turn, since dsh's own code executor runs it.

Everything dsh splices into a running step is forwarded to Claude's stdin the moment it arrives, whoever sent it (a steer you typed, a child's `send_message`, a subagent's settlement notice, a job's finish line), so the CLI injects it at its own next tool call instead of waiting for the turn to end. The same message is skipped when dsh later delivers it at a boundary (a typed steer by its prompt's rpcId, a dsh message by its id). A forwarded message also asks the step to end at the CLI's next tool result so dsh can draw it. The step does not end there while a dialog is open for another call of the same batch, since that would cancel the dialog; it ends at the next tool result that finds none open. That request is dropped at every step dsh opens, since dsh draws everything pending before it opens one, and a request left standing would end a step dsh has nothing to follow with. A steer that carries a file or an image goes over stdin too, whole: each file as the `[File …]` text dsh itself would send, each image loaded from dsh's attachment store with the note naming its saved copy. On a dsh that cannot name a file that way, it waits for the CLI's next tool result instead, where dsh delivers it whole. When no tool call follows, the CLI answers the steer as a turn of its own, and the dsh turn that re-delivers the steer shows that answer. During a dsh tool the result goes back to Claude as text, so a steer with an image does not ride on it: it goes over stdin whole when dsh hands the result back, and the CLI takes it at its next tool call.

A steer you typed also shows in a card above the composer until Claude reads it, with Edit and Remove, and Edit all when more than one is waiting. Each asks the CLI for the message back first (`cancel_async_message`; a message with a file or image skips this, since it never went to the CLI); when the CLI answers that it already took it, nothing changes and the card says so. Edit then takes the message out of dsh's pending list as well, so nothing delivers it while the editor is open. Edit all joins the waiting messages one per line, as Claude Code's up arrow does. Save sends one message with your text through dsh's own steer, Cancel or Escape puts the originals back, and Remove drops them. A file or image on a held message stays on it: the card shows each one as a chip, Save swaps only the text, and a message whose text you clear still goes out with its attachments. dsh counts a send with a file or image as unfinished until it shows in the chat, so taking one back makes it put the text and the files back in the composer of the tab that sent it; the card takes that copy back out, so pressing Enter does not send it twice. If the card stops asking for a minute (the tab was closed), the originals go back on their own. While Claude is inside a dsh tool (a subagent, a relayed job or shell), a steer you type waits in dsh's own list and reaches Claude with the tool's result; the card lists it with Edit and Remove, and says that Send now waits for the tool, since the CLI cannot be cut short there without losing the tool's work. dsh's Queue mode already lets you edit a queued message; this card covers Steer, where the plugin hands the message to Claude straight away.

An edit can move a message between dsh's queue and its steer list. A command or skill typed while a turn runs always waits in the queue, since Claude Code expands one only at the start of a turn. Edit that row in dsh's queue so it no longer opens with `/name`, and it is plain text: with dsh's "Send behavior while busy" setting on Steer, the plugin takes it out of the queue and steers it, the same thing the row's own Steer button does. With the setting on Queue, dsh's default, it stays queued, as plain text typed then would. The other way round, a steer edited on the card into a Claude command or skill line leaves the steer list and waits in the queue for the turn to end. Only a row that began as a command is moved, whether you typed it as one or saved a steer as one, so a message you chose to queue as plain text is never steered for you (`src/adapter/lane.ts`).

Parallel dsh calls in one Claude step are gathered into one dsh step so dsh runs them in parallel. A step with a dialog still open (an approval, a question, a plan review) holds those calls until the dialog is answered, because ending the step would cancel it. Stop in dsh sends the CLI an interrupt and keeps the process for the next turn instead of killing it. A message sent while that turn ran, and already forwarded to the CLI, is not lost. The CLI runs it as a turn of its own after the interrupt, and its reply shows the way a background reply does. An error there is dropped the way a background error is. Forking a Claude session in dsh copies the parent's Claude transcript under the new id, cut at the forked turn, so the fork keeps Claude's context.

Three tools are the bridge's own, not dsh's. `open_session` starts a new top-level dsh session in the caller's workspace (optional `provider`, `model`, `reasoningEffort`, `agentPreset`, `workspaceId`; the effort applies only with a provider and model), sends it a first prompt, and returns the session id. It shows in the sidebar as its own row and runs on its own. `prompt_session` sends that session, or any other session but the caller's, a follow-up: `mode: "queue"` (the default) runs it after the current turn, `"steer"` injects it into the running one, and a cold session resumes first. Optional `provider`, `model` and `reasoningEffort` switch that session's model before the message goes in, for that session only; the default for new sessions does not change. The switch applies from the session's next step, as a switch in dsh's model picker does, so a turn already running continues on the new model. The session stays on the new model until it is switched again. A model without a provider keeps the session's provider, an effort alone keeps its model, and a different model without an effort runs at that model's default, while the same model keeps its effort. A different model has to be one dsh's picker lists, and the model has to take the effort, or the call is refused and nothing is sent. When the call switches the model, the reply names it. The message arrives under a line that names the sending session, so the session that receives it, and anyone reading its transcript, can tell it from something the owner typed. dsh's own `send_message` cannot do this, because it reaches only the caller's children and teammates. It returns a cursor. `wait_session` waits on dsh's `sessionController.wait` until the session goes idle or needs input, or the timeout passes (30 s by default, 240 s at most, since Claude's MCP client drops a call that stays silent for about 300 s), and returns the session's text replies after that cursor, oldest first. Thinking and tool calls are left out. One call returns at most 50 replies and 16,000 characters of reply text, the newest kept, and says when older ones were left out. Its first line ends with the cursor for the next call, so a wait that timed out picks up where it stopped and no reply is read twice. The tool refuses a cursor or timeout of the wrong type instead of dropping it. While the bridge is on, the appended system prompt also tells Claude to route every subagent through `mcp__dsh__*` and never through its own `Agent` tool, whose children dsh cannot see. It points at `mcp__dsh__list_subagent_models` for the allowed routes rather than naming any, and sends background commands to dsh's shell tool. The text is built from the tools the bridge lists for that session, so it names `mcp__dsh__pwsh` on Windows and leaves out a tool the session does not have. Switch off with `dshTools: false`. Source `src/mcp.ts`.

## Command bridge

The CLI's init frame lists its slash commands (skills, custom commands, built-ins such as `/compact`). Each name dsh's command grammar accepts is registered under its own name on first sight (default instance only), so the composer's slash menu offers `/verify`, `/context` and the rest under a description naming the Claude command. A name dsh's client already contributes, or one another host has registered, takes the `/claude-<name>` form instead, because dsh's command menu refuses a host command whose name matches a client-side contribution. A name dsh already offers as its own command (`/goal`, `/plan`, `/export`, `/feedback`, `/permission`) takes the prefixed form too, since dsh's registry keeps both and answers with its own. `/compact` is the exception: dsh's version condenses dsh's copy of the conversation, which Claude never reads, so in a Claude session the plugin mounts its own `compact` under the session's agent, where dsh's registry lets an agent-scoped command shadow the global one. Typed there, `/compact` goes to Claude Code, the same as the context card's button; after a switch to another model the same command runs dsh's own compaction. Running one hands `/name <arguments>` to Claude as the next prompt, where the CLI expands it exactly as the terminal would. The transcript shows `/name <arguments>` as the bubble you sent, and the composer shows `/name sent to Claude Code`. A skill created or edited from the Skills tab appears live through the same path: the plugin sends `reload_skills`, the CLI re-lists its commands, and the new skill's `/name` registers here without a respawn.

Session names travel both ways. A name typed into dsh's sidebar (a `session/title` event with the `user` source) goes to the session's process as `rename_session` just before the next prompt, so `claude --resume` lists the same name; dsh's generated and fallback titles stay in dsh, since sending them would overwrite the CLI's own auto title with the first prompt's words. In the other direction the CLI's `session_title_changed` frame, which carries a name someone set and never its generated title, renames the dsh session when it differs. The frame lands outside any turn (at startup when the session already has a name, and after each change), so the process consumes it the way it consumes a suggestion, and the echo of a rename the plugin itself sent compares equal and changes nothing.

Each bridged command declares `input.attachments`, so a file or image in the composer goes with it (dsh refuses attachments to a command that does not declare them, with `/name does not accept attachments`), and they reach Claude the way a typed turn's do. A bridged line with attachments is logged as a user turn rather than the collapsed notice row, so the bubble shows the file or image chip a typed prompt would. In a session on another model the bridged line goes to that model instead: a skill dsh serves itself is expanded by dsh's own `/name` gesture, and a skill or custom command only Claude Code has (the project's or the user's `.claude/skills/<name>/SKILL.md` or `.claude/commands/<name>.md`) goes with its instructions, frontmatter dropped and `$ARGUMENTS` filled in, as a second message in the `<skill_content>` shape dsh's skill injection writes, so the chat draws it folded. The Settings switch "Claude Code skills on every model" (the `claudeSkillsAnywhereOff` hint) turns that second case off, and the bridge refuses the name as before; an ssh box never reads this box's skill files for it. Renaming through the bridge sets dsh's title as well. `/claude-rename <title>` renames the dsh session first and sends the line only if that worked, so the two names cannot end up disagreeing, and dsh's title is pinned afterwards so automatic title generation stops replacing it. Switch off with `commandBridge: false`.

dsh lists these commands, and the plugin's own `/btw`, `/temporary` and `/ultracode`, in every session, whatever model it runs on. Typed in a session on another provider, each one answers `/<name> works in Claude Code sessions. This session runs on <provider>` and does nothing else, with one exception: when dsh itself serves a skill of that name (from its own skill folders, such as `~/.dsh/skills`), the line goes to the session as you typed it and dsh runs the skill on that session's model. The provider is the one dsh routes the session by: a model picked and not yet used, else the model of the last request, else dsh's default model.

## Auxiliary calls

dsh's session-title requests, and the compaction requests `cliCompaction` leaves to the one-shot summarizer ([Compaction](#compaction)), run as one turn with no tools and no session of their own, from a scratch directory so they never show up in a workspace's session list.

## Content search

dsh's sidebar search can search message content through its own FTS5 backend (`dsh-session-query-sqlite`), which dsh ships switched off (`openAt: never`). Turning it on is a dsh deployment setting in the profile's `cordis.patch.yml`, not something this plugin does or needs.

## Errors

Abort from the UI kills the child. Non-zero exits surface with the last stderr. A real usage limit surfaces as `RATE_LIMIT` with the provider's reset time as retry-after. The CLI answers a rejected request with its own synthetic message ("You've reached your Fable limit. Switch to another model, or manage usage credits at …"), and that text is relayed whole, whatever the cause it names. The failure row adds only what the event's own fields say: which window (`rateLimitType`), when it reopens, printed as the CLI's [error reference](https://code.claude.com/docs/en/errors#youve-hit-your-session-limit) does (`1pm` later today, `Tue 1pm` inside the week, `Sep 8, 1pm` beyond it) in the browser's zone, and "· continuing automatically when it resets" when the wait is on.

While the CLI retries a 429 or 5xx by itself, each attempt is one reasoning line with the wait, the reset clock (in the browser's zone dsh stamps on each prompt, else the box's) and the attempt count, so the turn never looks busy for nothing. A retry line for a 5xx also names the incident Anthropic's status page reports, if any.

With `continueAfterLimit` on, the plugin arms a timer for the reset (kept in `limit-waits.json`, so a restart re-arms it) and then drops a continue notice through the same path a restart uses. Any prompt sent before then cancels the wait. Before the notice goes out, the plugin checks that the session still runs on this provider (a reroute to another model drops it) and asks the usage endpoint whether a window is still at its cap (then the wait is re-armed for that reset). A rejected request that paid extra usage covers is not a limit at all, so the turn goes on as in the CLI. Extra usage turned on during a wait needs no detection, since any prompt cancels the wait and Claude's next limit event says whether credits cover the overflow.

## Surviving Claude Code updates

The Claude Code terminal UI updates itself. A headless `claude -p`, which is what this plugin runs, never does (measured on 2.1.273, 2026-09-16: the updater is a component of the terminal UI). So the plugin stands in for it. A minute after boot and every 30 minutes, the CLI's own cadence, this dsh reads the release pointer the CLI reads (`downloads.claude.ai/claude-code-releases/<channel>`, unless `DISABLE_AUTOUPDATER` or `DISABLE_UPDATES` is set, which the CLI honours too) and asks `claude --version` on this box and on every saved ssh box.

When a session's box is behind, a card above the composer names the box and both versions with an Update button, which runs `claude update` there from dsh, an Always update link that also flips the box's Update on its own switch, and a dismiss that holds until the next release. The new version is a link to that release's entry on code.claude.com's changelog. Folding the card to its header is kept on the box for that release too, so it stays folded across sessions and tabs until a newer release opens it again. The same button sits on each Boxes row in Settings, beside Log out. Every run is recorded under the plugin's state directory (`claude-updates.json`). The Claude Code updates switch in Settings holds the rest under an Options fold that reads out the current choices: a box picker when there is more than one box, the release channel (the `autoUpdatesChannel` key in that box's settings.json, which the CLI's own updater follows too), Update on its own (on, the next half-hourly check installs without the card), and a History fold of the last ten runs beside a Check now button that re-reads the release pointer without installing. A run the CLI declines (a package-manager install, a `minimumVersion` cap, a slower channel) is recorded with the CLI's own words and not offered again for that release. A running session finishes on the version it started with. The next spawn picks up the new one, and the plugin forgets that box's flag probe so the next spawn reads the new binary. The Claude Code updates switch in Settings turns the whole thing off.

On first use per process the adapter reads `claude --help` and `--version`, and any flag the installed CLI does not list is left out (`--effort`, `--append-system-prompt`, `--include-partial-messages`, `--max-budget-usd`, session flags). Without `--input-format` the prompt goes positionally and images are skipped. Whole-message fallback covers a CLI that stops sending partial events. Started session ids are kept in `~/.local/state/dsh-oh-my-claude/sessions.json`, and a `--resume` the CLI rejects is retried once as a fresh run. Model ids and effort levels come from the Models API, so new models need no code change. The version in use is logged at first request.

## Plugin updates

`dsh plugin --profile web update dsh-oh-my-claude` and a restart of `dsh web` bring in a new version. Neither npm nor dsh announces one, so the plugin does. An orange pill with the new version number appears beside the Oh My Claude heading in Settings, and on the panel's Runtime line, once a newer release is on npm (one registry read a day, from the dsh server). A click opens the plugin's page in dsh's Plugins panel through dsh's `pluginNavigation` service, and closes Settings or the panel so the page is not behind them; dsh's Update button there installs the release with dsh's own registry checks. The copy button beside the pill puts the update command on the clipboard instead. DSH Desktop's CLI refuses its profile, so there the pill has no copy button and the Plugins page is the only route. A dsh without the plugin manager has no `pluginNavigation`, and the pill then copies the command on click, as it did before. The Update notice switch at the top of that settings section turns the read off, and the pill then only names the running version. The pill also reads the new release's dsh floor off its package.json on the registry. When this box's dsh does not reach it, the pill offers no command, because a plugin that needs a newer dsh than the box has would replace a working one with a broken one, and says "1.6.0 needs dsh 0.2.2-alpha.2" as plain text instead; the command comes back once dsh is updated. A dsh upgrade, as opposed to a plugin one, can call for one repair, described next.

## Failed to load history after a dsh upgrade

dsh 0.1.5 gave the session log a versioned format with a strict migration. Logs written with `toolsInline: false` before 2026-09-08 hold raw `tool/call` rows the migration refuses, and dsh then shows *Failed to load history … does not match one advertised tool call* for that session. The plugin repairs these itself: when it starts (a sweep over every stored log, fifteen seconds after boot), when a session is opened from the Restore tab, and when a restart wakes a session dsh refuses. Each repair is proved through dsh's own loader before and after it writes, the original is kept beside the log as `.bak`, and the panel's Runtime line says what was repaired. A refusal the plugin does not recognise is reported there and on the Restore tab instead of a silent failure to open, and the log is left as it is. A log refused for a reason the plugin cannot mend gets a Reseed from transcript button on that line: the click moves the log to `.bak` and seeds the session again from its Claude Code transcript, so the turns come back while the old log's dsh-only rows (subagents, permissions, the title, tool cards) stay in the `.bak`. Nothing reseeds on its own. Opening a session from the Restore tab also folds in the turns its transcript gained since the session was last in dsh, so one driven from the terminal in between shows the whole conversation; the one shape it cannot tell apart is two different prompts with the same text, where the later one reads as already stored. From a checkout, the same repair runs by hand, with dsh-web stopped, for a box where dsh cannot be restarted or the plugin is not installed:

```sh
bun tools/dsh-session-repair.ts --check --all   # lists what needs repair, changes nothing
bun tools/dsh-session-repair.ts --apply --all   # drops the offending rows, keeps a .bak next to each log
```

The tool proves every repaired log through dsh's own migration chain before writing it. Conversation text is untouched, and only the tool cards of those old turns are gone from history.

The same tool mends a second break: *stored log is corrupt: … system/message requires a protected first surface head*. A session restored from a Claude Code transcript before plugin 1.3.2 was seeded without the system-prompt head dsh keeps as the log's first entry. It worked until its first live turn wrote one further down, and from the next reload on (a dsh-web restart, another browser or phone opening it) dsh refused the whole log. `--check --all` lists every such log, refused or not yet, and `--apply --all` inserts the head; nothing else in the log changes.

And a third: *stored log is corrupt: … step/end leaves unresolved tool call*. Before plugin 1.3.2, a Stop pressed while one of Claude's own tools was running ended the step with that tool's call open, and dsh refuses a log whose step ends that way. `--apply --all` closes each such call with the same placeholder result the plugin now writes itself, right before the step's end; the conversation text and every other row stay as they were.
